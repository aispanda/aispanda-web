## Exact consumer onboarding

Use this sequence when another repository needs to ask the localhost governance gate for a decision. This is registration to request a decision, not build, commit, merge, deployment or secret authority.

1. Add one reviewed entry to `GOVERNANCE_CONSUMER_PROFILES` in `server/governance-consumers.mjs`. Supply only a unique non-secret webhook path, the exact lowercase `github.com/<owner>/<repository>` identity, approved actions, one approved caller (or the established unrestricted-caller compatibility value), and the current policy and story-contract versions. The generated route fixes that profile before reading request data. Never add a wildcard, credential, secret, prompt, caller-supplied profile or dynamic discovery rule.
2. Add positive normalization and exact-match tests plus denial tests for lookalikes, alternate hosts, extra path segments, encoded paths, wildcards, unsupported actions/callers, bad versions and self-registration. A fictional portability consumer belongs only in test configuration.
3. Regenerate the inactive parent candidate with `node scripts/build-ai95-parent-candidate.mjs`, then run `npm run test:governance` and `git diff --check`. The generated candidate—not a manually edited workflow—is the review artifact.
4. Before localhost import, export the currently active parent and record its workflow ID, credential and baseline-child bindings, plus a redacted baseline row count/hash. Keep that export as the rollback copy.
5. Import the regenerated parent as inactive. Preserve the existing consumer's Header Auth binding; bind every new consumer route to its own Header Auth credential, then bind only the existing read-only Linear and baseline-child references. A shared key must not identify two consumers. Test denials first: cross-profile impersonation, unregistered/lookalike repository, wrong action/caller/version and unavailable dependency must fail closed and write no baseline. Then test the existing consumer and the new exact consumer.
6. Activate or replace the live parent only after explicit human approval. Re-run the existing consumer regression, the new consumer positive request and an exact-operation retry; roll back immediately if an old outcome changes or an unapproved request passes.
7. Record sanitized evidence: workflow/execution IDs, exact repository/branch/full HEAD, policy and contract versions, `PASS`/`FAIL`, stable violation codes, baseline row count/hash, rollback result and test totals. Never record tokens, credential values or full story text.

AI-93 live positive and negative authorization evidence is recorded in [`AI_93_GOVERNANCE_MVP_EVIDENCE.md`](AI_93_GOVERNANCE_MVP_EVIDENCE.md).
