# Architecture Decisions

Status: Current decision register
Scope: AIspanda content, identity, collaboration and community platform

Owner approval recorded 2026-08-16: Google sign-in for staff now, with provider-flexible community identity later.

This document owns accepted solution decisions and their reasons. `SITE_FOUNDATION.md` owns the public-site baseline. Detailed behavior belongs in `CONTENT_AUTHORING_REQUIREMENTS.md`; delivery order belongs in `PRODUCT_ROADMAP.md`.

| ID | Status | Decision | Value and reason |
|---|---|---|---|
| AD-001 | Accepted | Keep the public site static-first on Astro, Nginx and Cloud Run. | Preserves the existing fast, low-runtime public site and validated deployment path. |
| AD-002 | Accepted | Add Firebase Authentication and Firestore alongside Cloud Run; do not replace Cloud Run. | Firebase supplies managed identity and cross-device draft persistence while Cloud Run continues to host the site and privileged publishing operations. |
| AD-003 | Accepted | Start staff access with Google sign-in, but keep identity provider-flexible for future community members. | Gives owners and authors the simplest first experience without forcing every future commenter or community member to use one provider. |
| AD-004 | Accepted | Use five roles: `Administrator`, `Publisher`, `Author`, `Commenter` and `View Only`. A verified new account starts as `Commenter`, may request an editorial role, and only an existing Administrator may approve or change roles. | Gives new members a safe useful default while preventing self-escalation into writing, publishing or administration. |
| AD-005 | Accepted | Enforce authorization in Firestore security rules and Cloud Run APIs, not only in interface visibility. | A modified browser must not be able to read drafts, change roles or publish content. |
| AD-006 | Accepted | Keep privileged actions in Cloud Run: publishing, deployment, role administration, moderation automation and security-sensitive mutations. | Repository and deployment authority never enters browser code. |
| AD-007 | Accepted | Use Firestore for structured drafts, comments and initial group/discussion data, with bounded queries, pagination, retention and cost monitoring. | Supports multi-user capabilities with low initial operations; usage controls protect cost as activity grows. |
| AD-008 | Accepted | Published titles open the read-only public version; editing requires an explicit `Edit` or `Edit draft` action. A never-published draft is the only title that may open directly in the editor. | Navigation communicates the destination before the user acts. |
| AD-009 | Accepted | Treat no-cost quotas as an initial operating benefit, not a permanent cost promise. | Authentication, database and compute usage can exceed provider free quotas as comments or chat activity grows. |
| AD-010 | Accepted | Extract a reusable, brand-configurable content and community asset only after AIspanda proves the implementation and verification gates pass. | Prevents an unproven prototype or project-specific assumptions from becoming a reusable dependency. |
| AD-011 | Accepted | Collect necessary identity, role, security and audit data at sign-in; keep outreach consent separate and optional; do not infer sensitive beliefs for targeting. | Supports operations and useful analysis without turning participation in AI, spiritual or accountability communities into undisclosed sensitive profiling. |
| AD-012 | Accepted | Launch the private Studio at the protected `/studio` route and expose `Sign in` when signed out, `Content Studio` when authorized, and contextual `Edit article` controls only to authorized staff. | Welcomes Commenters and View Only members without implying editorial access; role checks still protect Studio and editing controls. |
| AD-013 | Accepted | Commit only Firebase's public web identifiers in `.env.production`; keep authorization in Firestore rules and private role records. | Ensures clean Cloud Build containers can initialize sign-in without treating client-visible identifiers as secrets or exposing private access data. |
| AD-014 | Accepted | Use one Google continuation flow for account creation and sign-in, followed once by optional native dropdowns for professional role, primary interest and UN M49/ISO country or area; do not retain profile photos. | Keeps onboarding short, analyzable and privacy-conscious while avoiding duplicate auth choices, unnecessary image data and third-party country-list dependencies. |
| AD-015 | Accepted | Own the article comments UI and permission logic; store bounded threads in Firestore rather than adopting a hosted comment plug-in. Keep public comment content separate from private ownership records. | Reuses the existing Google identity and roles, avoids another account/vendor, protects stable account identifiers, keeps the experience brand-consistent and preserves a future storage-migration path. |
| AD-016 | Accepted | Build the first community experience as durable Groups containing titled Discussions and contextual Posts, not as an unstructured live-chat stream. `Thread` may remain an internal implementation term, but the interface uses `Discussion`. Administrators and Publishers may create Groups; every signed-in role except View Only may participate in permitted Groups. | Gives members plain, predictable language and makes conversations searchable and useful over time while preserving a later seam for optional real-time chat. |
| AD-017 | Accepted | Apply ownership rules consistently across article comments and community Posts: members may edit or delete only their own words; Administrators may delete any Post for moderation but may never rewrite another member's words. | Protects authorship, keeps moderation accountable and prevents elevated roles from silently changing what someone said. |
| AD-018 | Accepted | Treat Events and Learning paths as optional modules on the shared identity, role, notification and discussion foundation. A published Learning path contains ordered Sections and Lessons; `My learning plan` is the member's personal progress view, not a second content type. Start with RSVP Events and self-paced Learning paths only after the core community is proven. | Adds useful community depth without burdening the first discussion release with live-streaming, payments, recurrence, cohorts or scheduled content release. |
| AD-019 | Accepted | Make AI connections provider- and router-neutral behind a small connector contract for authentication, capabilities, status and generation. Implement managed connectors with direct standards-compatible HTTP before adding LangChain or LangGraph. | Users can choose routers and models without coupling product behavior to one vendor, while avoiding dependencies that do not yet earn their complexity. |
| AD-020 | Accepted | Let users fund their own AI usage. Prefer OpenRouter OAuth with S256 PKCE and offer an expert fallback for an existing API key. During the MVP, keep the returned or entered API key only in same-tab `sessionStorage`; never place it in Firestore, drafts, `localStorage`, logs or documentation. Clear it on disconnect, sign-out or tab close. Replace this with an encrypted server-side account vault before promising cross-device persistence. | Removes AI billing liability from AIspanda, lets a connection survive same-tab navigation and refresh, and keeps the temporary compromise explicit rather than creating misleading permanent storage. |
| AD-021 | Accepted | Keep light personal information on `/account` and place AI connections plus the comparison Playground together on `/ai`. Keep connection setup contextual and simple: Not connected, Connected, Active, or Needs attention; allow several same-tab connections but only one active router; expose manual keys only as an advanced option. Preserve `/account/ai-playground` as a redirect. | Separates identity from AI work while keeping the connect-compare-activate decision in one predictable place without duplicating systems or losing old links. |
| AD-022 | Accepted | Make Hugging Face connection OAuth-first through AIspanda's public no-secret OAuth application and S256 PKCE, request only `inference-api`, and retain a manually entered fine-grained token as a fallback. Keep the returned token in the same tab under AD-020's storage boundary. | Gives members one-click, least-privilege access to Inference Providers without AIspanda holding a client secret. |
| AD-023 | Accepted | Do not offer LiteLLM as a member connection in the initial product. Preserve the generic connector seam, but reconsider LiteLLM only for a separately approved, customer-operated enterprise deployment. | Self-hosting or supporting a user-operated gateway would add infrastructure, security, CORS, key-management and support responsibility that conflicts with the present no-liability goal. |
| AD-024 | Accepted | Provide a signed-in AI Router Playground for a user-written prompt of at most 300 characters, with one explicit suggested prompt. A member may run the active router or compare selected connected routers concurrently using the same bounded request (80 requested output tokens and a 500-character display limit). Use a router-column/metric-row comparison matrix and show each field once: routing method, model ownership, usage type, fallback, infrastructure provider, time to first response, output speed, reasoning tokens, reported cost and token use. Explain directionality, mark the best complete comparable value green and the weakest red, and leave informational or incomplete comparisons neutral. Keep answer quality outside the matrix: routers do not judge one another, and the member may mark a temporary preferred answer after reading both. Label missing values `Not reported`, isolate partial failures, link identities and a small curated set of benchmark/model sources, and let the member explicitly activate a successful connected router after comparison. Do not calculate unreported prices, create a combined winner score, persist prompts/results/preferences or retry through another router. A same-model comparison is deferred. | Turns connection testing into useful, transparent learning while keeping usage small, user-funded and provider-neutral; a scan-friendly matrix and honest per-aspect markers make trade-offs clear without presenting a false universal winner or circular AI quality score. |
| AD-025 | Accepted, interim cost boundary | Persist an activated user-funded AI-router connection across sign-out, browser closure and devices until the member explicitly disconnects, subject to provider expiry/revocation or a security-required reconnect. Store provider credentials only in an authenticated encrypted server-side account vault; keep ciphertext and metadata inaccessible to browser clients; return status or server-relayed results rather than stored credentials; and make disconnect remove the vault entry and revoke provider access when supported. For the current low-usage phase, the owner explicitly accepts the existing default Firestore database and its free quota instead of a separate billable database. The dedicated Cloud Run identity therefore has database-wide server access; this is an accepted interim risk, not a protection supplied by spending-limit disclaimers. Revisit the dedicated database before wider member onboarding or material credential volume. | Removes repeated setup without moving long-lived provider credentials into `localStorage`, client-readable Firestore documents, logs or generated content. Sign-out ends the application session but does not silently revoke the member's separate provider decision. The interim choice avoids a named-database charge while preserving encryption, browser denial and a dedicated runtime identity, but has a larger server-side blast radius than the preferred isolated-database design. |

## Activated foundation (2026-08-16)

- Firebase was added to the existing `aispanda` Google Cloud project; Analytics was left disabled.
- The `AIspanda Web` app and Google authentication provider were enabled.
- Authorized domains are `localhost`, `127.0.0.1`, `aispanda.com` and Firebase defaults.
- Firestore Standard was created in `us-east1`, matching Cloud Run, and production-deny-by-default rules were published.
- Two initial administrator invitations were created privately; each verified invitee claims a UID-based role record on first successful sign-in. User records remain outside version-controlled documentation.
- Verified accounts without an invitation receive Commenter access and may keep one current editorial-role request. They may cancel and re-submit it, but deployed Firestore rules reserve approval and role changes for existing Administrators.
- The first article discussion uses two-level threads, one like per eligible member, top-level pins for Publishers/Administrators, owner-only editing, owner deletion and Administrator deletion. Administrators cannot rewrite another person's comment. Deleted text becomes a thread-preserving tombstone.

## Target responsibility boundary

```text
Public website and Studio UI   Astro + Nginx on Cloud Run
Sign-in and sessions           Firebase Authentication
Drafts, comments and messages  Firestore
Authorization                  Role/access records + security rules + API checks
Publishing and moderation      Privileged Cloud Run services
User-funded AI routing         Browser connector -> user's selected router
Release                        Existing repository + Cloud Build path
```

## Reusable extraction boundary

The future reusable core may include configurable content types, rich-text authoring, books, comments, Groups, Discussions, Learning paths, authentication adapters, role policies, moderation states, publishing adapters and verification suites.

It must exclude domains, brands, editorial content, user records, credentials, cloud project values, repository identifiers and project-specific evidence. Named future consumers are validation candidates, not reusable-core configuration.
